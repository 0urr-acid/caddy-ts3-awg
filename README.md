# caddy-ts3-awg

Caddy модуль для UDP-пересылки TeamSpeak 3 / AmneziaWG 3.1 на одном внешнем порту.
Module ID и глобальная опция Caddyfile: **`ts3_awg`**.

```text
Клиент → Caddy UDP :9987 → TS3 :9988       (пакеты №1 и №2)
                       → проверка №3
                         ├─ AWG initiation + MAC1 → AWG :51820, затем весь поток
                         └─ остальное            → TS3, затем весь поток
```

Проверяется именно третий **клиентский** пакет. Ответы сервера не учитываются
в счётчике и не задерживают переключение. Учитываются `S1`, диапазон `H1`,
ChaCha20-защита заголовка и MAC1 по публичному ключу сервера. Пакет при
пересылке не изменяется. Приватный VPN-ключ серверу Caddy не требуется.

Новый 34-байтовый `TS3INIT1` этапа `00` до переключения начинает отсчёт заново
для повторной попытки. После переключения всё идёт в AWG без классификации;
запоздавшие ответы закрытого TS3-сокета отбрасываются. У каждого `IP:UDP-порта`
свой backend-сокет. Исходный IP до TS3 не сохраняется; в аудит-логах Caddy он
сохраняется как `remote_ip`.

## Сборка

Требуется Go **1.26+**. Зависимости закреплены в `go.mod` / `go.sum`;
проверено с **Caddy v2.11.9**.

```bash
make build
./bin/caddy list-modules
```

`make build` собирает обычный Caddy со стандартными модулями и этим плагином.
В списке модулей должна быть строка `ts3_awg`.

Для сборки через xcaddy из локальной папки:

```bash
xcaddy build v2.11.9 \
  --output bin/caddy \
  --with github.com/0urr-acid/caddy-ts3-awg=.
```


## Настройка

Минимальный рабочий пример:

```caddyfile
{
    ts3_awg {
        server vpn {
            listen udp/:9987
            teamspeak 127.0.0.1:9988
            awg 127.0.0.1:51820
            initiation {
                server_public_key {env.AWG_SERVER_PUBLIC_KEY}
                header_protection_key {env.AWG_HEADER_PROTECTION_KEY}
                s1 24
                h1 1
                random_trailers true
            }
            idle_timeout 2m
            max_sessions 1024
            audit {
                window 10s
                burst 60
                max_sources 16384
            }
        }
    }

    log ts3_awg_security {
        include ts3_awg
        output file /var/log/caddy/ts3-awg.json
        format json
        level INFO
    }
}
```

Можно объявить несколько именованных `server` с разными listener. Backends
задаются буквальными IPv4/IPv6 адресами: `127.0.0.1:9988` или `[::1]:9988`.
Hostname backend и диапазоны портов не поддерживаются. Ссылка backend на
этот же listener отклоняется при проверке конфига.

Полный пример для отдельного релея: [examples/Caddyfile](examples/Caddyfile).
Второй пример — глобальный блок для добавления к существующим site blocks;
он требует уже установленных сторонних модулей. Этот репозиторий их не включает.

| Поле | Значение по умолчанию / смысл |
|---|---|
| `listen` | Обязательно; `:9987`, `udp/0.0.0.0:9987`, `udp6/[::]:9987` |
| `teamspeak`, `awg` | Обязательные разные IP:port |
| `initiation.server_public_key` | Публичный ключ **AWG-сервера**, base64, 32 байта |
| `initiation.header_protection_key` | Общий ключ защиты заголовков, base64, 32 байта; можно не задавать, если защита выключена |
| `initiation.s1` | `0`; обязан совпадать с сервером, при защите заголовка ≥12 |
| `initiation.h1` | `1`; число uint32 или диапазон `min-max` |
| `initiation.random_trailers` | `false`; принимает дополнительный хвост после 148-байтового initiation |
| `idle_timeout` | `2m` от последнего пакета клиента |
| `max_sessions` | `1024` активных UDP-потоков на listener |
| `audit.window` | `10s` — окно подсчёта новых сессий/повторных I1 |
| `audit.burst` | `60` — число стартов с одного IP за окно, после которого пишется событие |
| `audit.max_sources` | `16384` — предел записей в счётчике IP; старые окна удаляются |

Клиент AWG должен отправлять **ровно `I1`, `I2`, затем initiation**: `Jc=0`,
без `I3–I5`. Обычный WireGuard без двух приманок на первом пакете не переключится.
Потери и перестановка UDP могут сорвать попытку; повторный `I1` позволяет
попробовать снова на том же исходном порту. MAC1 используется для выбора backend,
а не для аутентификации клиента: полноценную проверку Noise выполняет AWG.

TS3 и AWG должны слушать другие порты; backend AWG не следует публиковать
вместо релея. Для sing-box-lx backend на loopback отключи серверный
`route.auto_detect_interface`, как в работающем standalone-примере.
`127.0.0.1` требует общего network namespace: отдельные Docker-контейнеры
так не соединяются. IP forwarding и MASQUERADE для самого релея не нужны.


## Логи

Логи пишутся через штатный logger Caddy, имя **`ts3_awg`**. Например:

```json
{"level":"warn","ts":1794153600,"logger":"ts3_awg","msg":"suspicious UDP connection rate","server":"vpn","listen":"udp/:9987","event":"suspicious_connection","reason":"session_start_rate","remote_ip":"198.51.100.23","remote_port":21001,"attempts":61,"threshold":60,"window_seconds":10}
```

Событие возникает при превышении порога новых UDP tuple или повторных `I1`
с одного IP. Пишется **не более одного события на IP за окно**. Голосовые
пакеты существующей TS3-сессии, обычные команды, неуспешная проверка третьего
пакета и ошибки backend сами по себе не являются атакой и не идут на бан.
Большой NAT с множеством легитимных клиентов может потребовать более высокого
`burst`; UDP-источник до аутентификации может быть подделан.


## Reload и остановка

Неизменённые relay-настройки разделяют listener через `caddy.UsagePool`,
поэтому reload не сбрасывает AWG-сессии. При откате
неудачного reload ссылки и logger старой конфигурации восстанавливаются.
Остановка последнего владельца закрывает listener, backend-сокеты и читателей.

**Изменение настроек или имени действующего relay на том же listener требует
перезапуска Caddy.** Такой reload отклоняется, старая конфигурация продолжает
работать. Это предотвращает смешивание framing/ключей старых и новых сессий.
Новые listener можно добавлять, удалённые освобождаются при Stop.

## Проверки

```bash
make verify
make test
make vet
make build
python3 scripts/test-caddy.py
```

Проверяются независимый Noise initiation (Python hashlib/cryptography),
MAC1, nonce, ключи, H1, trailers, третий пакет, повторный I1, неизменность
датаграмм, изоляция клиентов, таймаут, Caddyfile, rate-аудит и reload.
`test-caddy.py` запускает настоящий собранный Caddy на временных localhost-портах,
проверяет совместную работу HTTP/UDP и реальный JSON audit event. Сертификаты
не выпускаются и внешние серверы не используются. Полный handshake с живым
AWG backend в тестах не подменяет отдельную эксплуатационную проверку.
